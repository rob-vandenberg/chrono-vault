# D-055: File dialogs as Chrono Viewer's

Approved by the owner on 23 November 2026 (Proceed, version 0.2.51).

Qt Quick's FileDialog is the system's own dialog on Linux only with the GTK+ platform theme (Qt's documentation); on
KDE it fell back to Qt's QML dialog: a path bar that cannot be typed in and a few places, so a vault on pCloud could
not be reached. Chrono Viewer, the owner's own program, solved this; its way is taken over (`src/places_here.*`,
`src/file_pickers.cpp` there).

1. Every file dialog of Chrono Vault (12: create, open and choose vaults, the keyfiles, import, export, attachments,
   icons) is Qt's widget dialog, always Qt's own window (`DontUseNativeDialog`), in Fusion, with an address field
   that can be typed in. `qml/FilePicker.qml` has the properties Chrono Vault used of FileDialog;
   `src/ui/file_pickers.*` shows the dialog.
2. The places down its left side (`src/ui/places_here.*`): on Linux / first, then the desktop's own list
   (`user-places.xbel`, the one Dolphin shows; only folders on this machine, not the hidden ones, each once, at most
   60; nothing from a file over 1 MB), or the usual folders where there is none; on Windows This PC, the usual
   folders and every drive. No disk is asked whether a place exists (OR-5).
3. The list of places opens as wide as its widest entry, at most a third of the dialog.
4. Each dialog first opens at 880 by 640 times the UI scaling, and opens again at the size and place it was left at,
   kept per dialog in `chrono-vault.ini`.
5. On Windows every file dialog is Explorer's own (the owner, 23 November 2026, version 0.2.52): it brings its own
   places, look and size, so points 1 to 4 apply on Linux only. Point 7 holds on both.
6. A dialog opens again in the folder last chosen in it, as Qt's own did (review round 1).
7. A lock (or any change of the vault's state) while a dialog is open closes it as Cancel; nothing it was asked for
   is done for a vault that has locked (review round 1).

**Since 0.5.79** Chrono Vault no longer creates the dialog's own Qt window before Explorer's dialog opens; Qt gives it
its owner. The dialog stays Explorer's own (the owner, 24 November 2026). 0.5.79 named that window as the cause of a
file dialog that opened invisible on one of the owner's Windows computers. **That was wrong**: 0.5.79 did not fix it.

**Since 0.5.80** every thread that talks to Windows Hello closes down its COM set-up when it ends
(`src/ui/quick_unlock_windows.cpp`). Measured with a small test program on that computer, twice, five dialogs a run:
no Windows Hello check, 5 of 5 shown; the check as Chrono Vault made it at every start, the run hung; the same with COM
kept for the whole program, the run hung; with COM closed down by the thread, 5 of 5; with the thread kept alive, 5 of 5.
The windows of the hung runs were not inspected, and why an unclosed thread stops Explorer's dialog is not known.
