# D-057: WebDAV storage

Approved by the owner on 23 November 2026 (Proceed, version 0.3.60). `ROADMAP.md` step 11, `REQUIREMENTS.md` 5.1.2
and 5.4, D-005, D-054, OR-15. Where the reference program's public help answered, its way was taken (ref, OR-16);
Q1 to Q3 were settled by the coder at the owner's word ("find out yourself"), from the reference program's security
whitepaper and forum.

## How it is built

1. **WebDAV is spoken with Qt Network**, no further library (OR-6): PROPFIND, GET, PUT, MOVE, DELETE, LOCK and
   UNLOCK, never waited for on the window's thread (OR-5) (`src/ui/webdav_client.*`).
2. **A working copy on this device** (REQUIREMENTS 5.4.3): a vault kept on a server is an ordinary encrypted vault
   file in the program's data folder (`…/chrono-vault/webdav/`); every unlock, save and merge uses it as a local
   vault, so the vault also works offline. A vault moved there from this computer keeps its own file as working copy.
3. **The base for merging** (D-054) is kept as a vault file of its own, `<id>.base.chronovault`, the last version
   this device and the server agreed on.

## When it syncs (ref)

4. At every unlock, every 10 minutes while unlocked, within 5 seconds of a save, and with Tools > Sync Now (Ctrl+J).
5. The server's version is downloaded only when its version tag changed. Nothing changed here since the last sync:
   the server's version becomes the working copy as it is. Otherwise both are merged as D-054, and the merge goes up
   only when it holds something the server's version lacks (so two devices never send it back and forth).
6. **An upload never replaces another device's version** (OR-15): written under a temporary name, read back and
   opened (OR-15.2), then moved into place under a WebDAV lock; a server without locks gets its tag checked right
   before the move. A tag changed meanwhile starts a new round (download, merge), at most three, then "Busy".
7. The working copy is always written here first; a change made offline, during a lock or before Quit goes up at
   the next sync. A sync stopped at any step loses nothing; tested at every step (OR-15.4).
8. **The server's version with another master password**: this device's version is kept beside the working copy as
   "<name> (conflict yyyy-MM-dd HH.mm).chronovault" and joins the list of vaults; the server's version becomes the
   working copy, and the vault locks and says so (as D-032 point 3). A server's version that cannot be read is
   never written over.

## What the person sees

9. New vault… and Open vault… first ask where: "On this computer…" or "On a WebDAV server…" (ref, 5.4.1). WebDAV
   asks the folder's address, user name and password, with Connect (ref); then the new vault's name (never one
   already in the folder) and the master password as for a file, or the vault to open from the folder's list.
10. Several vaults may share one folder, each its own file (ref).
11. **Settings > Vaults** (ref): each vault, where it is kept, "Last synchronized" (ref), "Move to WebDAV…" for a
    vault on this computer (5.4.4) and "Disconnect…" with "Also delete the vault on the server", off by default (ref);
    after a disconnect the vault stays on this computer.
12. Under the vault's name in the left column: "WebDAV" for a vault kept there, and "Not synchronized: <reason>"
    while the server cannot be used; the vault keeps working.

## Settled by the coder (Q1 to Q3)

13. **Q1, the WebDAV password**: on this device only, in the system's store: the desktop keyring (Secret Service)
    on Linux, the Credential Manager on Windows (`src/ui/secret_store*`), never in a settings file nor on the
    server. The reference program's whitepaper: access to a cloud account "is stored securely only on your device".
    Where no store answers, the password is asked once per run and kept in memory only. A password the server
    refuses is asked again.
14. **Q2, a certificate the system does not trust**: its SHA-256 fingerprint is shown and the person asked to trust
    it; the answer is kept per vault, and another certificate asks again. The reference program offers "Bypass SSL
    certificate verification", which drops every check; pinning was taken as clearly safer (OR-16.3), as the
    reference program itself pins certificates for its business server.
15. **Q3, plain http**: allowed, as in the reference program (its forum advises http for Synology and Nextcloud
    without SSL), with a warning in the window that the WebDAV user name and password cross the network readable.

## Taken while building

16. The working copy is written by the save thread, after any save of the window's (D-032 point 7); when the sync
    wrote it, the vault shown is read again, or merged with a change waiting here (D-054).
17. The temporary upload is named "<file>.<id>.uploading" per vault and device, so a stopped sync leaves at most one
    such file, replaced by the next.
18. A folder that is not there is not made: "Create it there first" (ref: "a folder you've created specifically
    for your vault").
19. Only the vault shown syncs; another vault syncs when it is shown.
