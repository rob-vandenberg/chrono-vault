# D-054: Merging

Approved by the owner on 23 November 2026 (Proceed, autonomous mode, version 0.2.45). `ROADMAP.md` step 10,
`REQUIREMENTS.md` 5.3, D-005, OR-15. The reference program's merge rules are not public and its code is closed
(OR-2), so the owner let the coder decide Q7 to Q10 and accepted all four recommendations.

## What was decided

1. **Merging is automatic, part of syncing**: the person never starts it. It happens wherever D-032 made a conflict
   copy: a change made elsewhere while a change waits here, the check right before every save, and a change kept
   through a lock.
2. **A three-way merge**: this device's version and the other one are compared with the last version both agreed on
   (the base). A change made on one side only is taken.
3. **The same value changed differently on both (Q7)**: the newest change stands; the other value goes into the
   field's history and stays in a note on the item, "“<field>” was changed on two devices. The newest change stands;
   the other was: …", with "Use the other value" and OK. The list shows a red dot on such an item. Fields are judged
   by their own change time; the title, subtitle, note and website by the item's.
4. **Deleted on one device, changed on the other (Q8)**: the change wins; the item stays, with the note "Deleted on
   one device and changed on another, so it was kept.", Delete Permanently… and Keep.
5. **Deletions travel (Q9)**: contents format 7 keeps the id and time of every item deleted for good, for good.
6. **No File > Merge with… (Q10).**
7. Parts merged: items by id; within an item each text, the category, template, favourite, Trash, Archive,
   Autosubmit and icon; fields by their id, with their order from the side that changed it; field history as the
   union of both; attachments by id; tags as a set; the person's own categories and templates by id; the hidden
   categories and the vault's icons as sets.
8. A message says that both versions were merged, and how many items carry a note.

## Taken in autonomous mode

1. **The base is kept in memory, not in a file**: a local vault file is written right after every change, so the
   base is always the version this Chrono Vault last read or wrote; a change kept through a lock keeps its base
   sealed with it. A base on disk comes with the working copy of WebDAV and the cloud storages (D-005, 5.4.3).
   So changelist item 12 (interrupted writes of the base) has nothing to test: the merge adds no write step; the
   merged vault is written by the atomic, verified save that every save uses (OR-15).
2. The merge is made on the window's thread (it touches no disk and decrypts nothing); the other version is read
   on the save thread (OR-5). A save queued before a merge was taken in is passed over; the save after the merge
   holds its change.
3. With no base (none known), a difference is settled by the newest and noted, as a conflict.
4. A conflict in the category, template, favourite, Trash, Archive, Autosubmit, icon, a template or a category of
   the person's own is settled by the newest change without a note: there is no text to show.
5. The other version that cannot be read with this key (another master password, a newer format, damaged or half
   written) still gives the conflict copy of D-032, so nothing is lost.
6. A merge's message stays after the save that follows it.
7. **Since 0.5.76 (D-060)** the note on an item is no longer settled on the item itself but in the Sync conflicts
   dialog (Tools > Sync Conflicts…, or Settle… on the item), after Chrono Mail's: per field or per item, the value now
   or the other value, or both kept as two items.
